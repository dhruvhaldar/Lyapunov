## 2024-07-30 - [Redundant Pydantic Validators]
**Vulnerability:** A DoS protection `@model_validator` in Pydantic checking `duration / dt > 100000` was mathematically unreachable because individual field limits (`le=100.0` and `ge=0.001`) already enforced this exact maximum boundary.
**Learning:** Pydantic validators designed for composite constraints (like ratios) must use thresholds stricter than the implicit maximums defined by their constituent fields, otherwise they provide false confidence and act as security theater.
**Prevention:** Always calculate the worst-case boundary conditions of individual fields before implementing cross-field validation, ensuring the custom validator actually catches cases the basic field constraints miss.
## 2026-08-03 - [JSON Serialization Crashing on Pydantic Validator Exceptions]
**Vulnerability:** When a custom Pydantic `@model_validator` raises an exception (like `ValueError`), FastAPI's default exception handler or a custom `RequestValidationError` handler must serialize the error context. If the custom handler fails to stringify the inner `Exception` object, `json.dumps()` raises a `TypeError` (e.g., 'Object of type ValueError is not JSON serializable'), crashing the request with a 500 error instead of a graceful 422.
**Learning:** Python `Exception` objects are not inherently JSON serializable. Custom sanitization logic in exception handlers must explicitly check for and handle `Exception` types.
**Prevention:** Always include an `elif isinstance(obj, Exception): return str(obj)` clause in recursive dictionary sanitizers designed for error responses to safely unpack context without causing downstream serialization failures.
## 2026-08-05 - [SymPy Nested Power DoS Bypass]
**Vulnerability:** The existing DoS protection logic in the `check_stability` endpoint used `isinstance(node.exp, sp.Pow)` to prevent deeply nested powers. This could be bypassed if the power operation was hidden inside another mathematical expression (like multiplication `x**(2*y**z)` or addition `x**(y**z + 1)`), leading to an `Add` or `Mul` node as the exponent and evading the check. This allowed an attacker to execute a resource exhaustion DoS attack during SymPy `lambdify`.
**Learning:** Checking the immediate type of a child node is insufficient for detecting deeply nested mathematical operations in ASTs (Abstract Syntax Trees) like SymPy.
**Prevention:** Use recursive tree-search methods like `node.exp.has(sp.Pow)` to ensure that any instance of a forbidden operation is detected regardless of how deeply it is nested or obfuscated within other operations.
## 2024-10-25 - [SymPy Evalf/N DoS Vulnerability]
**Vulnerability:** SymPy's `parse_expr` internally resolves method calls like `.n()` or `.evalf()` on safe mathematical constants (e.g., `E`, `pi`) *during the parsing step itself*, even if `evaluate=False` is set. An attacker can craft payloads like `E.n(100000000)` which will exhaust CPU and memory resources immediately during parsing, bypassing any AST traversal checks that run afterward.
**Learning:** `parse_expr(evaluate=False)` does not protect against method execution if dot-notation is allowed in the input expression string.
**Prevention:** Strictly forbid attribute access patterns in the input string via regex (e.g., `re.search(r'\.\s*[a-zA-Z_]')`) *before* passing the string to `parse_expr` to prevent method invocation while still permitting standard decimal numbers (`1.5`) and scientific notation (`1.0e3`).
## 2026-10-06 - [SymPy Scientific Notation DoS]
**Vulnerability:** Parsing excessively large scientific notation floats (e.g., `1e999999`) via SymPy's `parse_expr` causes severe CPU exhaustion because it forces the creation of a massive `Float` object even when `evaluate=False` is set. An attacker can hang the server thread and max out CPU indefinitely by simply submitting standard scientific notation format.
**Learning:** SymPy's parsing rules immediately evaluate the precision and magnitude of floats, including scientific notation. Regular integer limits do not apply here.
**Prevention:** Strictly validate and reject excessively large scientific notation exponents using regex (e.g., `r'\d\.?\d*[eE][\+\-]?\d{4,}'`) before allowing the string to be passed to `parse_expr` to prevent thread pool starvation and DoS.
## 2026-10-07 - [Global DoS via Rate Limiter Dictionary Exhaustion]
**Vulnerability:** The custom IP-based rate limiter in the FastAPI middleware capped its internal tracking dictionary at 10,000 entries to prevent OOM errors, but returned a global `429 Too Many Requests` for all new IPs once full. An attacker could trivially execute a Denial of Service (DoS) against the entire application by spoofing 10,000 unique IPs, permanently locking out all legitimate users until the garbage collection cycle ran.
**Learning:** Hard limits on security caching mechanisms (like rate limiter dictionaries) must fail open or evict data gracefully (e.g., LRU eviction). Failing closed on a cache boundary weaponizes the security mechanism into a global DoS vector.
**Prevention:** When capping memory structures for IP tracking, always evict the oldest entry (e.g., using `next(iter(dict))`) rather than denying service to new, unrecognized traffic.
